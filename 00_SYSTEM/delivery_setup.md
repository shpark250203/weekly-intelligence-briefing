## 4. 자동 실행 방식 비교 — A(로컬) vs B(클라우드)

> **본 절은 설계안이다. 실제 스케줄·클라우드 리소스는 생성하지 않았다.**

### 4-1. 개요

| | **A. Windows PC 기반** | **B. Cloud 기반 (Claude Code Routine)** |
|---|---|---|
| 실행 주체 | 내 PC의 Windows 작업 스케줄러 | Anthropic 클라우드의 격리 세션(CCR) |
| PC 전원 | **켜져 있어야 함** | 불필요 |
| 로컬 폴더 | 그대로 사용 | **접근 불가** |

### 4-2. 필요한 구성

**A. Windows PC 기반**

1. Windows 작업 스케줄러 작업 1건 — 매주 월 08:00 KST
2. 래퍼 스크립트(PowerShell) — `claude -p "/weekly-brief"` 를 헤드리스로 실행
3. 실행 권한 사전 허용 (`--allowedTools` 또는 `settings.json` permissions)
4. 발송 단계 (아래 4-6 참조)
5. 로그 파일 경로 지정
6. 전원 옵션 조정 — 절전 해제 허용, 최대 절전/종료 시에는 동작하지 않음

**B. Cloud 기반**

1. **선결 조건 — 프로젝트를 git 저장소로 만들고 GitHub private repo에 푸시**
   현재 이 폴더는 git 저장소가 아니다. 클라우드 세션은 로컬 폴더에 접근할 수 없으므로,
   `CLAUDE.md` · `.claude/skills/weekly-brief` · `00_SYSTEM/*` 가 repo에 있어야 동일 품질 기준으로 동작한다.
2. Routine 생성 — `environment_id`, `cron_expression`(UTC), 자기완결형 프롬프트
3. `sources`에 git repository URL 지정
4. `mcp_connections`에 **Gmail 커넥터 연결** (§5 참조)
5. 모델 지정 (기본 `claude-sonnet-5`)
6. 결과 아카이브 경로 결정 — repo 커밋 / PR / 메일만

> 월요일 08:00 KST = **일요일 23:00 UTC** → cron `0 23 * * 0`
> (07:00 KST 원하면 `0 22 * * 0`. Routine 최소 간격은 1시간이며 주 1회는 제약 없음)

### 4-3. 장점

| A | B |
|---|---|
| 로컬 폴더를 그대로 쓴다 — `01_WEEKLY_BRIEFS/` 아카이브가 자동 적재됨 | **PC 전원과 무관하게 실행** — 발행 시각 보장 |
| `CLAUDE.md` · Skill · 템플릿이 이미 있는 자리에서 그대로 적용됨 | 프로젝트가 보관할 secret이 **0건** (커넥터 방식) |
| git 저장소가 필요 없다 — 구조 변경 없음 | 실행 환경이 매주 동일하게 초기화됨 (로컬 상태 오염 없음) |
| 추가 과금·외부 인프라 없음 | 실행 기록이 서버에 남아 웹 UI로 조회 가능 |
| 실패 시 로컬에서 즉시 재실행·디버깅 가능 | 노트북 이동·네트워크 변경에 영향받지 않음 |

### 4-4. 단점

| A | B |
|---|---|
| **월요일 08:00에 PC가 켜져 있어야 한다** — 이 프로젝트의 목적(발행 시각 고정)과 정면 충돌 | **선결 조건이 있다** — git 저장소화 + GitHub 푸시 |
| 최대 절전·종료 상태에서는 "절전 해제" 옵션도 동작하지 않음 | 로컬 폴더 접근 불가 → 아카이브 경로를 새로 설계해야 함 |
| 노트북 덮개 닫힘 / 전원 분리 / 출장 시 실패 | **내장 자동 재시도가 없다** — 재시도를 직접 설계해야 함 |
| 로컬 네트워크·브라우저 상태에 따라 매체 접근 결과가 흔들림 | 클라우드의 웹 접근 환경이 로컬과 달라 `Access Blocked` 패턴이 바뀔 수 있음 |
| PC 상시 가동 시 전기료 | Routine 삭제는 CLI 불가 — 웹에서만 |
| 헤드리스 세션에서 Gmail 커넥터 가용 여부 **미검증** | 클라우드 세션은 길어 구독 사용량 소모가 큼 |

### 4-5. 비용

| 구분 | A | B |
|---|---|---|
| 외부 인프라 비용 | **0원** | **0원** (GitHub private repo 무료) |
| Claude 사용량 | 구독 사용량 차감 (주 1회) | 구독 사용량 차감 (주 1회, 로컬보다 세션이 길어질 여지 있음) |
| 전기료 | PC 상시 가동분 발생 | 없음 |
| 실질 추가 비용 | 전기료 + PC 가용성 관리 부담 | 초기 git 구성 1회 공수 |

→ **두 방식 모두 별도 과금은 없다.** 비용 차이는 금액이 아니라 **PC를 켜 두는 제약**과 **초기 구축 공수**다.

### 4-6. Gmail 발송 방식

**A. Windows PC 기반 — 두 갈래**

- **A-1 (선호)**: 헤드리스 `claude -p` 세션에서 **claude.ai Gmail 커넥터**로 발송
  → 저장할 secret 없음. 단 **헤드리스 세션에서 커넥터가 로드되는지 미검증** — A 채택 시 최우선 검증 항목
- **A-2 (대안)**: 커넥터가 안 되면 PowerShell에서 **Gmail SMTP 직접 발송**
  `smtp.gmail.com:587` + STARTTLS + **2단계 인증 앱 비밀번호**
  (`Send-MailMessage`는 deprecated이며 한글 HTML 인코딩 이슈가 있어 MailKit 또는 `curl --mail-*` 권장)

**B. Cloud 기반**

- Routine의 `mcp_connections`에 **Gmail 커넥터를 연결**하면 클라우드 세션이 그대로 Gmail 도구를 사용해 발송한다.
- 별도 OAuth 앱·앱 비밀번호·SMTP 설정 **불필요**.

### 4-7. Secret 관리 방식

| | A-1 (커넥터) | A-2 (SMTP) | B (Cloud) |
|---|---|---|---|
| 저장되는 비밀정보 | 없음 (Claude 로그인 토큰만 `%USERPROFILE%\.claude`) | **앱 비밀번호 1건** | **없음** |
| 보관 위치 | — | Windows 자격 증명 관리자 또는 DPAPI 암호화 파일 | Anthropic 서버 측 커넥터 |
| 평문 파일 금지 | — | 프로젝트 폴더에 저장 금지 | — |
| `.gitignore` | 이미 `.env` · `token*.json` · `client_secret*` 차단 규칙 있음 | 동일 | 동일 |
| 유출 시 영향 | 낮음 | **중** — Gmail 발송 권한 탈취 가능 | 낮음 |

> A-2를 택하면 이 프로젝트가 **처음으로 장기 보관 secret을 갖게 된다.** 보안 부담이 실제로 늘어난다.

### 4-8. 실패 시 재시도

**A. Windows 작업 스케줄러 — 내장 기능으로 대부분 해결**

- "작업이 실패하면 다시 시작" — 재시도 간격·횟수 지정 (예: 15분 간격 3회)
- "예약된 시작을 놓친 경우 가능한 한 빨리 작업 실행" — **PC가 꺼져 있었다면 켜진 직후 실행**
  → 단, 월요일 09시를 넘겨서 켜면 **발행 마감을 놓친다.** 이 옵션은 지연 복구일 뿐 시각 보장이 아니다
- 최대 실행 시간 초과 시 강제 종료 설정

**B. Cloud Routine — 내장 재시도 없음. 직접 설계 필요**

- **권고 설계**: 2차 검증 Routine을 **월요일 09:30 KST (일 → 월 00:30 UTC, cron `30 0 * * 1`)** 에 배치
  → Gmail에서 해당 주차 제목의 메일이 존재하는지 확인 → 없으면 재생성·재발송, 그래도 실패하면 실패 알림 메일 발송
- 1차 Routine 자체에도 "발송 실패 시 재시도 1회 후 실패 보고 메일" 지시를 프롬프트에 명시
- 실패 원인 확인은 §4-9의 run log로

## 5. Gmail 인증 재사용 가능 여부 — 확인 결과

**질문: 지금 Claude Code에 연결된 Gmail MCP 인증을 클라우드 자동화에서 그대로 쓸 수 있는가?**

### 5-1. Claude Code Cloud Routine → **재사용 가능 (확인됨)**

계정에 연결된 claude.ai 커넥터 목록에 **Gmail이 등록되어 있고, Routine에서 사용 가능**함을 확인했다.

| 항목 | 값 |
|---|---|
| 커넥터명 | Gmail |
| `connector_uuid` | `997bf03d-6acc-47ea-b7dc-da7943ce5edb` |
| URL | `https://gmailmcp.googleapis.com/mcp/v1` |
| 사용 방법 | Routine 생성 시 `mcp_connections`에 위 3개 필드를 넣어 연결 |

- **별도 Gmail API OAuth 앱을 만들 필요가 없다.**
- 단, 이것은 "토큰을 복사해 옮기는" 것이 **아니다.** 내 claude.ai 계정에 이미 붙어 있는 커넥터를
  **같은 계정의 클라우드 세션에 연결해 쓰는 것**이다. 자격증명은 계속 Anthropic 서버 측에서 관리되며,
  파일로 내보내거나 다른 시스템에 붙일 수 없다.
- 따라서 **claude.ai에서 Gmail 커넥터 연결을 해제하면 Routine 발송도 즉시 중단된다.**

### 5-2. Anthropic 외부 런타임 → **재사용 불가**

GitHub Actions · Cloud Run · AWS Lambda · VPS · n8n 등 **Anthropic 밖에서 돌리는 자동화에는
이 커넥터 인증을 가져다 쓸 수 없다.** refresh token과 client secret이 서버 측에 있고 내보낼 수 없기 때문이다.

외부 런타임을 쓰려면 **별도의 안전한 인증 수단을 새로 만들어야 한다.**

| 방식 | 내용 | 적합성 |
|---|---|---|
| **① Gmail API OAuth (권장)** | 자체 Google Cloud 프로젝트 → OAuth Client(Desktop) 생성 → `gmail.send` scope 동의 → **refresh token** 확보 후 시크릿 저장소에 보관 | 개인 Gmail에 사용 가능 |
| **② Gmail SMTP + 앱 비밀번호** | 2단계 인증 활성화 후 앱 비밀번호 발급, `smtp.gmail.com:587` | 간단하나 권한 범위가 넓음 |
| **③ 서비스 계정 + 도메인 위임** | — | **개인(소비자) Gmail 계정에는 사용 불가.** Google Workspace 전용 |

어느 쪽이든 자격증명은 **평문으로 프로젝트 폴더에 두지 않는다.**
(GitHub Actions Secrets / Secret Manager / Windows 자격 증명 관리자)
`.gitignore`에는 이미 `credentials*.json` · `client_secret*` · `token*.json` · `refresh_token*` 차단 규칙이 있다.

### 5-3. 로컬 헤드리스 실행 → **미검증**

`claude -p` 헤드리스 세션에서 claude.ai Gmail 커넥터가 로드되는지는 **확인하지 않았다.**
A안을 택할 경우 **가장 먼저 검증해야 할 항목**이며, 실패하면 §4-6의 A-2(SMTP + 앱 비밀번호)로 전환해야 한다.
→ 즉 **A안은 secret 보관이 필요해질 가능성을 안고 시작한다.**

## 6. 권고안

### 결론: **B (Cloud Routine)** 를 채택한다.

**근거**

1. **이 프로젝트의 산출물은 "월요일 09시 이전에 도착하는 메일 1통"이다.**
   발행 시각이 목적 그 자체인데, A는 그 시각의 PC 전원 상태에 성패가 달린다.
   A의 최대 단점이 프로젝트 목적과 정면으로 충돌한다.
2. **Gmail 재인증이 필요 없다.** §5-1에서 커넥터 재사용 가능이 확인됐다.
   B의 진입장벽으로 예상했던 인증 문제가 실제로는 없다.
3. **보관해야 할 secret이 0건이다.** 반대로 A는 커넥터가 헤드리스에서 동작하지 않으면
   앱 비밀번호를 장기 보관해야 한다(§5-3).
4. 남은 선결 조건(git 저장소화)은 **1회성 작업**이며, 아카이브 버전 관리라는 부수 이득이 있다.
   §2-3의 rev 불일치 같은 문제도 git 이력으로 추적 가능해진다.

**단, 즉시 전면 전환하지 않는다.**

클라우드 세션의 웹 접근 환경은 로컬과 다르므로, 5개 뷰티 전문매체 접근 결과와
Tier 1 직접 확인률이 로컬 대비 떨어질 수 있다. 이것은 실행해 보기 전에는 알 수 없다.
